# SMPB

**SMPB** — лёгкое модульное ядро на C++23 для моих проектов. Ядро крутит цикл с фиксированной частотой тиков (TPS) и управляет набором **компонентов**: инициализирует их, вызывает на каждом тике, передаёт между ними **задачи** и корректно завершает их работу.

## Возможности

- Главный цикл с фиксированной частотой тиков, контролем нагрузки и предупреждением о пропущенных тиках.
- Компонентная архитектура: каждый модуль наследуется от `BaseComponent` и реализует `init` / `tick` / `death`.
- Безопасное добавление компонентов в любой момент, в том числе из `init()`, `tick()` и обработчиков задач: новые компоненты попадают в очередь и подключаются в начале следующего тика.
- Изоляция компонентов: они не имеют прямого доступа к ядру и работают с ним только через API-методы `Core_*`.
- Система задач: компоненты отправляют друг другу задачи (`BaseTask`) по имени получателя.
- Автоматическое удаление компонентов, вернувших ошибку.
- Настройка через текстовый файл `core.config`.
- Режим отладки с подробным логом каждого тика.
- Возможность статической сборки под Linux и Android (aarch64).

## Сборка

### Требования

- CMake 3.16 или новее
- Компилятор с поддержкой C++23 (проверено на GCC 15)
- Ninja или Make

### Обычная сборка

```bash
cmake -S . -B build -G Ninja
cmake --build build
```

Если `CMAKE_BUILD_TYPE` не задан, по умолчанию используется `Release`. В `Release` включается межмодульная оптимизация (LTO), если компилятор её поддерживает: она нужна, чтобы методы `Core_*` встраивались в код компонентов. Для LTO с GCC нужен `gcc-ar`; если его нет, CMake собирает проект без LTO.

Отладочная сборка:

```bash
cmake -S . -B build-debug -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build-debug
```

Для сборки через Make флаг `-G Ninja` не указывается, а в папке сборки запускается `make`.

### Сборка под Android (aarch64)

В репозитории есть `android.toolchain.cmake` для NDK r27 со статической линковкой. Компиляторы `aarch64-unknown-linux-android-gcc` и `aarch64-unknown-linux-android-g++` ищутся в `PATH`:

```bash
cmake -S . -B build/Android -G Ninja -DCMAKE_TOOLCHAIN_FILE=android.toolchain.cmake
cmake --build build/Android
```

Если компиляторов нет в `PATH`, каталог с ними задаётся через `ANDROID_TOOLCHAIN_DIR` — параметром CMake или переменной окружения. Поиск идёт в самом каталоге и в его подкаталоге `bin`:

```bash
cmake -S . -B build/Android -G Ninja -DCMAKE_TOOLCHAIN_FILE=android.toolchain.cmake -DANDROID_TOOLCHAIN_DIR=/путь/к/toolchain
```

Если компиляторы не найдены, CMake завершается с ошибкой.

Файл `AndroidFix.cpp` содержит заглушку `__libcpp_verbose_abort`, которую требует линкер Android при статической сборке через NDK r27. Toolchain-файл выставляет переменную `SMPB_ANDROID`, и только при ней `AndroidFix.cpp` добавляется в сборку. Кроме того, код внутри файла обёрнут в `#ifdef __ANDROID__`, поэтому на других платформах он пустой.

## Запуск

```bash
cd build
cp ../core.config .
./smpb
```

`core.config` ищется в **текущей рабочей папке**, поэтому программу нужно запускать из папки, где он лежит. Программа работает бесконечно, пока какой-либо компонент не вызовет `Core_stop()`; остановить её вручную можно через `Ctrl+C`.

## Файл конфигурации `core.config`

Текстовый файл, одна команда в строке, формат `КОМАНДА АРГУМЕНТ`. Слова разделяются пробелами или табуляцией, допускаются окончания строк как `\n`, так и `\r\n`. Читаются только первые два слова строки, остальные игнорируются. Строки, где нет команды или аргумента, пропускаются.

| Команда                     | Аргумент                     | Статус             | Описание                          |
|-----------------------------|------------------------------|--------------------|-----------------------------------|
| `SET_TPS`                   | целое число без знака        | работает           | Задаёт количество тиков в секунду |
| `SET_DEBUGMODEENABLED`      | `TRUE` / `FALSE`             | пока не реализована | Включение режима отладки          |
| `LOAD_DLL`                  | путь к библиотеке            | пока не реализована | Загрузка внешнего модуля          |

Пример:

```
SET_TPS 20
SET_DEBUGMODEENABLED TRUE
LOAD_DLL Base/Userlib.dll
```

Для каждой команды компонент `Config` выводит результат: `executed!`, `no valid value!` или `unknow command!`.

Пока `SET_DEBUGMODEENABLED` не реализована, режим отладки включается в `main.cpp` вызовом `core.setDebugModeEnabled(true)`.

## Архитектура

```
                 ┌──────────────────────────────┐
                 │             Core             │
                 │  цикл тиков, TPS, debug-режим│
                 │  список и очередь компонентов│
                 └──────┬───────────────▲───────┘
        init/tick/death │               │ Core_* API, sendTask
                        ▼               │
       ┌──────────────────┐   ┌──────────────────┐
       │  Config          │   │    Компонент     │   ... (наследники BaseComponent)
       └──────────────────┘   └──────────────────┘
                 │                      ▲
                 └──── BaseTask ────────┘   задачи передаются через Core
```

### Жизненный цикл

1. **Создание.** В `main()` создаётся `Core`, в него добавляются компоненты через `appendComponent()`. Добавленные компоненты сначала попадают в **очередь** `componentsQueue`, а не сразу в список `componentsList`.
2. **Инициализация** — `Core::init()`. Компоненты по порядку переносятся из очереди в список: у каждого вызывается `setCore()`, компонент добавляется в список, затем вызывается `init()`. Поэтому уже в `init()` компонент может отправлять и получать задачи. Если `init()` вернул не 0, у компонента вызывается `death()` (он ещё в списке и тоже может отправлять задачи), после чего он удаляется из списка.
3. **Работа** — `Core::cycle()`. В начале каждого тика очередь переносится в список так же, как в `Core::init()`, поэтому новые компоненты тикают уже в этом тике. Затем у всех компонентов по порядку вызывается `tick(tickCounter)`. Если `tick()` вернул не 0, у компонента вызывается `death()` и он удаляется, а ядро продолжает работу.
4. **Остановка.** Когда кто-то вызвал `Core::stop()` (или `Core_stop()` из компонента), цикл заканчивает текущий тик и по порядку вызывает у каждого компонента из списка `death()`, сразу после чего компонент уничтожается. Поэтому в `death()` задачи можно отправлять только компонентам, которые ещё не уничтожены. Компоненты, оставшиеся в очереди, удаляются без вызова `death()`, так как они не проходили `init()`. Затем цикл возвращает 0.
5. **Уничтожение ядра.** Если `Core` уничтожается, а компоненты ещё остались (например, `cycle()` не запускался или завершился с ошибкой), деструктор `~Core()` завершает их так же, как при остановке: вызывает `death()` и уничтожает компоненты. Компоненты, добавленные из деструкторов других компонентов, тоже корректно удаляются.

Компонент, добавленный во время тика, не виден через `findComponentIdxByName()` и не может получать задачи, пока его не перенесут из очереди в начале следующего тика.

### Тайминг

Длительность тика равна `1000 / TPS` миллисекунд и хранится как дробное число, поэтому TPS, на который 1000 не делится нацело, выдерживается точно: например, при 30 TPS тик длится 33.333… мс, а не 33 мс. Расписание тиков тоже ведётся в дробных наносекундах. После каждого тика ядро спит до момента начала следующего (`sleep_until`), поэтому частота не плавает от того, сколько длился сам тик.

Если тик занял больше отведённого времени, ядро сдвигает расписание вперёд на всё отставание, и потерянное время не догоняется. Отставание в тиках, обычно дробное, прибавляется в накопитель `skippedTicksAccumulator`. Как только в нём набирается хотя бы один целый тик, выводится жёлтое предупреждение с целым числом пропущенных тиков, а дробный остаток остаётся в накопителе и учитывается при следующих отставаниях:

```
Warning: 2 ticks are being skipped. Performance issues!
```

Например, при отставании на 0.3 тика каждый тик предупреждение `1 ticks` появляется примерно раз в 3–4 тика, а при отставании на 2.5 тика выводится поочерёдно `2` и `3`. Накопитель обнуляется при каждом запуске `Core::cycle()`. Пропущенные тики не увеличивают `tickCounter`: он считает только выполненные тики.

В режиме отладки после каждого тика выводится строка с номером тика, ожидаемым TPS, фактической длительностью и процентом загрузки. Дробные значения выводятся с 3 знаками после запятой. Строка формируется через `std::format`, поэтому настройки формата `std::clog` не меняются и не влияют на вывод компонентов:

```
Tick #12 end; Expected TPS: 20; Tick duration: 0.013 ms, 0.000 ticks (util: 0.026%)
```

## Справочник по классам

### Core

`Core/Core.h`, `Core/Core.cpp`

Центральный класс: хранит компоненты, крутит главный цикл и маршрутизирует задачи. Копирование запрещено.

#### Поля (private)

| Поле                | Тип                                            | По умолчанию | Описание                                   |
|---------------------|------------------------------------------------|--------------|--------------------------------------------|
| `ticksPerSecond`    | `uint32_t`                                     | `5`          | Тиков в секунду                            |
| `debugModeEnabled`  | `bool`                                         | `false`      | Режим отладки                              |
| `stopFlag`          | `bool`                                         | `false`      | Флаг остановки цикла                       |
| `target_duration`   | `std::chrono::duration<double, std::milli>`    | `200.0`      | Длительность одного тика в дробных миллисекундах |
| `skippedTicksAccumulator` | `double`                                 | `0.0`        | Накопитель пропущенных тиков: дробный остаток, ещё не выведенный в предупреждении |
| `componentsList`    | `std::vector<std::unique_ptr<BaseComponent>>`  | пусто        | Активные компоненты; индекс в векторе служит id компонента |
| `componentsQueue`   | `std::vector<std::unique_ptr<BaseComponent>>`  | пусто        | Очередь добавленных компонентов, ожидающих переноса в `componentsList` |

#### Методы

| Метод | Описание |
|-------|----------|
| `Core()` | Конструктор. Ничего не делает. |
| `~Core()` | Деструктор. Завершает оставшиеся компоненты через `destroyComponents()`. |
| `int setTPS(uint32_t tps)` | Задаёт TPS и пересчитывает `target_duration = 1000.0 / tps` мс без округления (при `tps == 0` получается 0 мс). Возвращает `0`. |
| `int setDebugModeEnabled(bool n_debugModeEnabled)` | Включает или выключает режим отладки. Возвращает `0`. |
| `int stop()` | Ставит флаг остановки. Цикл завершится после текущего тика. Возвращает `0`. |
| `uint32_t getTPS() const` | Текущий TPS. |
| `bool isDebugModeEnabled() const` | Включён ли режим отладки. |
| `void appendComponent(std::unique_ptr<BaseComponent> component)` | Добавляет компонент в конец очереди `componentsQueue`, ядро становится его владельцем. Пустой указатель не добавляется: в `cerr` пишется `Error in Core::appendComponent: component is nullptr`. В список компонентов он попадёт в `Core::init()` или в начале следующего тика. Вызывать можно в любой момент, в том числе во время обхода компонентов. |
| `int findComponentIdxByName(const std::string& name) const` | Ищет компонент по имени. Возвращает индекс первого компонента с этим именем или `-1`, если компонента нет. |
| `int findComponentIdxByPtr(const BaseComponent* component) const` | Ищет компонент по указателю. Возвращает индекс или `-1`, если компонента нет в списке (или передан `nullptr`). |
| `int processTask(std::unique_ptr<BaseTask> task)` | Передаёт задачу компоненту-исполнителю (`workerIdx`), сразу вызывая его `processTask()`. Если индекс отправителя или исполнителя вне списка или компонент по этому индексу уже уничтожен, возвращает `-ENOENT`. Если исполнитель вернул ошибку, пишет её в `cerr` и возвращает тот же код. При успехе возвращает `0`. |
| `int init()` | Переносит очередь компонентов в список через `processComponentsQueue()`. Возвращает `0`. |
| `int tick(long long tickCounter)` | Сначала переносит очередь компонентов в список через `processComponentsQueue()`, затем вызывает `tick(tickCounter)` у каждого компонента. Компоненты, вернувшие ошибку, получают `death()` и удаляются. Возвращает `0`. |
| `int cycle()` | Главный цикл: обнуляет `skippedTicksAccumulator`, тикает, следит за временем, спит до следующего тика, накапливает пропущенные тики и выводит предупреждение о целом числе пропусков, выводит статистику в режиме отладки. После остановки завершает компоненты через `destroyComponents()` и сбрасывает `stopFlag`. Возвращает `0` или код ошибки `tick()`. |
| `int processComponentsQueue()` *(private)* | Переносит все компоненты из `componentsQueue` в `componentsList`. Для каждого вызывает `setCore(this)`, добавляет компонент в `componentsList` и вызывает `init()`. Если `setCore()` вернул ошибку, компонент удаляется, не попав в список. Если ошибку вернул `init()`, сначала вызывается `death()`, потом компонент удаляется из списка. Компоненты, добавленные во время этого переноса (например, из `init()` другого компонента), обрабатываются в том же вызове. Возвращает `0`. |
| `void destroyComponents()` *(private)* | Завершает компоненты: по порядку вызывает `death()` у каждого компонента из списка и сразу уничтожает его, затем очищает список. После этого очищает очередь без вызова `death()`, пока она не станет пустой, включая компоненты, добавленные из деструкторов. Вызывается из `cycle()` при остановке и из `~Core()`. |

### BaseComponent

`Core/BaseComponent.h`, `Core/BaseComponent.cpp`

Базовый класс всех компонентов. Хранит имя компонента и указатель на ядро, даёт наследникам API для работы с ядром и виртуальные методы жизненного цикла.

#### Поля

| Поле            | Доступ      | Тип           | Описание |
|-----------------|-------------|---------------|----------|
| `core`          | `private`   | `Core*`       | Указатель на ядро, по умолчанию `nullptr`, задаётся через `setCore()`. Наследникам недоступен. |
| `componentName` | `protected` | `std::string` | Имя компонента. По нему компонентам адресуются задачи, поэтому оно должно быть уникальным. |

#### Основные методы

| Метод | Описание |
|-------|----------|
| `BaseComponent(std::string name)` | Конструктор. Сохраняет имя и пишет в лог `[name] My constructor executed!`. |
| `virtual ~BaseComponent()` | Виртуальный деструктор. |
| `const std::string& getName() const` | Имя компонента. |
| `std::string getPrefix() const` | Префикс для логов вида `"[Имя] "`. |
| `int setCore(Core* t_core)` | Привязывает компонент к ядру. Вызывается ядром при переносе компонента из очереди в список, вручную вызывать не нужно. Возвращает `0`. |

#### API ядра (методы `Core_*`)

Через эти методы компонент обращается к ядру. Ядро становится доступно после `setCore()`, то есть начиная с `init()` компонента. До этого, например в конструкторе, методы ничего не делают и возвращают значение из колонки «Без ядра».

| Метод | Что вызывает в ядре | Без ядра |
|-------|---------------------|----------|
| `int Core_setTPS(uint32_t tps)` | `Core::setTPS` | `-ENOSYS` |
| `int Core_setDebugModeEnabled(bool n_debugModeEnabled)` | `Core::setDebugModeEnabled` | `-ENOSYS` |
| `void Core_stop()` | `Core::stop` | ничего не делает |
| `uint32_t Core_getTPS() const` | `Core::getTPS` | `0` |
| `bool Core_isDebugModeEnabled() const` | `Core::isDebugModeEnabled` | `false` |
| `void Core_appendComponent(std::unique_ptr<BaseComponent> component)` | `Core::appendComponent` | ничего не делает, компонент уничтожается |

#### Задачи

| Метод | Описание |
|-------|----------|
| `int sendTask(std::unique_ptr<BaseTask> task, const std::string& workerName)` | Отправляет задачу компоненту с именем `workerName`: проставляет в задаче `creatorIdx` (индекс отправителя, ищется по указателю `this`) и `workerIdx` (индекс получателя, ищется по имени), затем вызывает `Core::processTask`. Возвращает код, который вернул обработчик, `-ENOSYS`, если компонент ещё не привязан к ядру, `-EINVAL`, если `task` пустой, или `-ENOENT`, если отправитель или получатель не найден в списке компонентов. |
| `virtual int processTask(std::unique_ptr<BaseTask> task)` | Обработчик входящих задач, переопределяется в наследнике. Реализация по умолчанию пишет ошибку и возвращает `-ENOSYS`. |

#### Методы жизненного цикла (переопределяются в наследнике)

| Метод | Когда вызывается | Реализация по умолчанию |
|-------|------------------|-------------------------|
| `virtual int init()` | Один раз при переносе компонента из очереди в список: в `Core::init()` или в начале тика | В режиме отладки пишет `I'm init!`, возвращает `0` |
| `virtual int tick(long long tickCounter)` | На каждом тике, `tickCounter` — номер тика с 0 | В режиме отладки пишет `I'm tick!.`, возвращает `0` |
| `virtual void death()` | Перед удалением компонента: при ошибке в `init()` или `tick()`, при остановке ядра или при уничтожении ядра | В режиме отладки пишет `I'm death!` |

Если `init()` или `tick()` вернёт не `0`, ядро удалит компонент.

### BaseTask

`Core/BaseTask.h`, `Core/BaseTask.cpp`

Базовый класс задачи, которую один компонент передаёт другому. Для передачи данных создаётся наследник с нужными полями.

#### Поля

| Поле         | Доступ      | Тип        | По умолчанию | Описание |
|--------------|-------------|------------|--------------|----------|
| `taskIdx`    | `protected` | `uint32_t` | —            | Номер задачи, задаётся в конструкторе. Смысл определяет отправитель, например тип задачи или её id. |
| `creatorIdx` | `private`   | `int`      | `-1`         | Индекс компонента-отправителя |
| `workerIdx`  | `private`   | `int`      | `-1`         | Индекс компонента-исполнителя |

#### Методы

| Метод | Описание |
|-------|----------|
| `BaseTask(uint32_t t_taskIdx)` | Конструктор, задаёт номер задачи. |
| `virtual ~BaseTask()` | Виртуальный деструктор. |
| `uint32_t getIdx() const` | Номер задачи. |
| `int getCreatorIdx() const` | Индекс отправителя. |
| `int getWorkerIdx() const` | Индекс исполнителя. |
| `int setCreatorIdx(int t_creatorIdx)` | Задаёт индекс отправителя. Возвращает `0`. Обычно вызывается из `sendTask()`. |
| `int setWorkerIdx(int t_workerIdx)` | Задаёт индекс исполнителя. Возвращает `0`. Обычно вызывается из `sendTask()`. |

### Config

`Core/Config.h`, `Core/Config.cpp` — наследник `BaseComponent`, имя компонента `"Config"`.

Компонент начальной настройки: выводит аргументы командной строки и применяет команды из `core.config`.

#### Методы

| Метод | Описание |
|-------|----------|
| `Config(int argc, char *argv[])` | Конструктор. Выводит в лог все аргументы командной строки. |
| `int init() override` | Читает `core.config` через `readFile()`, разбивает на строки `КОМАНДА АРГУМЕНТ` и выполняет поддерживаемые команды (сейчас только `SET_TPS`). Для каждой команды пишет результат в лог. Если файла нет или его не удалось прочитать, пишет ошибку в `cerr`. Всегда возвращает `0`. |

### Функции tools.h

`Core/tools.h`, `Core/tools.cpp`. Вспомогательные функции, не привязанные к классам.

| Функция | Описание |
|---------|----------|
| `std::pair<std::vector<char>, int> readFile(const std::string& filename)` | Читает файл целиком в бинарном режиме. Возвращает `{содержимое, 0}` или `{пусто, код ошибки}`. Коды ошибок: `-EISDIR`, если это папка; `-errno` при ошибке открытия (например, `-ENOENT` — файла нет, `-EACCES` — нет прав); `-EIO`, если не удалось определить размер файла или прочитать его целиком. |
| `std::pair<std::string, int> readFile_S(const std::string& filename)` | То же самое, но содержимое возвращается как `std::string`. |

## Соглашения

- **Коды возврата.** `0` означает успех. Ошибки возвращаются как отрицательный `errno` из `<cerrno>`: `-EINVAL` (неверный аргумент), `-ENOENT` (не найдено), `-ENOSYS` (не реализовано или компонент не привязан к ядру).
- **Логи.** Информационные сообщения пишутся в `std::clog`, ошибки в `std::cerr`. Сообщения компонентов начинаются с `getPrefix()`. Отладочные сообщения выводятся только при `Core_isDebugModeEnabled()`.
- **Владение.** Компоненты и задачи передаются через `std::unique_ptr` и `std::move`. Ядро владеет компонентами, получатель задачи владеет задачей.
- **Имена компонентов** должны быть уникальными: задачи адресуются получателю по имени, и находится первый компонент с совпавшим именем. Отправитель определяется по указателю, поэтому `creatorIdx` всегда указывает на настоящего отправителя.

## Пример: компонент и задача

```cpp
#include "Core/Core.h"
#include "Core/Config.h"
#include "Core/BaseComponent.h"
#include "Core/BaseTask.h"

// Задача с данными
class PrintTask : public BaseTask {
public:
    PrintTask(std::string t_text) : BaseTask(1), text(std::move(t_text)) {}
    std::string text;
};

// Компонент, который принимает задачи
class Printer : public BaseComponent {
public:
    Printer() : BaseComponent("Printer") {}

    int processTask(std::unique_ptr<BaseTask> task) override {
        auto* printTask = dynamic_cast<PrintTask*>(task.get());
        if (!printTask) return -EINVAL;
        std::clog << getPrefix() << printTask->text << "\n";
        return 0;
    }
};

// Компонент, который отправляет задачи и останавливает ядро
class Sender : public BaseComponent {
public:
    Sender() : BaseComponent("Sender") {}

    int tick(long long tickCounter) override {
        sendTask(std::make_unique<PrintTask>("Тик " + std::to_string(tickCounter)), "Printer");
        if (tickCounter >= 9) Core_stop(); // Остановиться после 10 тиков
        return 0;
    }

    void death() override {
        std::clog << getPrefix() << "Завершаюсь\n";
    }
};

int main(int argc, char *argv[]) {
    Core core;
    core.appendComponent(std::make_unique<Config>(argc, argv));
    core.appendComponent(std::make_unique<Printer>());
    core.appendComponent(std::make_unique<Sender>());

    core.init();
    return core.cycle();
}
```
